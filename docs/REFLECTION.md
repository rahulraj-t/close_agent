# One-page reflection

**With 3 months instead of 8 hours.** (1) Build the Mapper agent properly: retrieval over COA + approved-mapping history, calibrated confidence, an offline eval set with false-auto-map rate as the headline metric. (2) The ledger-lines lineage store, so every statement cell is a query over source rows. (3) The Statement Builder + Verifier for all four statements, including cash flow (indirect method from balance movements) and SOCIE walk. (4) A reviewer UI for the exception queue with decisions stored as versioned data. (5) Policy as configuration: FX translation per account class, materiality, tolerance. (6) Property-based tests (Hypothesis) on balance invariants, and a replay harness over past closes.

**Where the prototype breaks at scale.** It is in-memory and single-entity. With 1000s of accounts the lexical suggestion heuristics become noise (needs embeddings plus structured features); `difflib` is quadratic. Multi-entity consolidation needs entity as a first-class dimension, per-entity functional currency, IC matching with timing differences, CTA computation and elimination journals, none of which exist here. Adjustment reasonableness checks are hard-coded for FX reval and depreciation; at scale they must be a rule library. The NI figure ignores unmapped accounts by design, which is only acceptable while the exception queue is small.

**How AI tools were used.**  It helped most with: enumerating seeded defects quickly, scaffolding the pipeline and tests, and drafting plain-English explanations. It led wrong in two places that I would watch for: the first instinct was to apply FX translation as the README says, which makes the TB *less* balanced, so the data had to overrule the instruction; and "helpful" auto-fixes for unbalanced entries (guessing the missing 3,500 line) are exactly what finance software must not do, so the design forbids them. All numbers in the docs were taken from program output, not recalled.

**What I think is underestimated.**  Almost every number depends on a policy the data does not state (FX basis, QTD vs YTD, pre/post close, who may approve a COA change). A system that silently picks one produces beautifully formatted wrong statements. The product's real value is making each assumption explicit, versioned, attributable to a person, and visible next to the number it affects, so that a statement is a *conclusion from recorded decisions* rather than the output of a black box.
